# MCP Tap (Max for Live)

Per-track signal tap for the ableton MCP. Drop **MCP Tap** onto any track
(including the Master). Each device self-identifies its track and streams audio
stats to a Python-hosted **registry** inside the MCP server over TCP
`localhost:9878`; the MCP metering tools read it.

> **Supersedes the v0.7.0 `MCP Audio Tap`** (which was master-only and acted as a
> TCP server). The model is now inverted: the MCP server hosts one registry and
> any number of tap devices connect in as clients. **Migration:** replace any
> `MCP Audio Tap` instance with `MCP Tap`.

## Install / use
1. Ensure Ableton Live **Suite** (Max for Live) is installed.
2. Drag `MCP Tap.amxd` onto a track (or the Master). Leave it enabled.
3. Run `get_audio_tap_status` / `list_taps` - the device appears with its
   resolved `index` + `kind` (`regular` / `return` / `master`).
4. `read_track_meter(track_index)` reads that track's signal summary
   (`-1` = master).

## How it works
- **Self-identification (no LOM path parsing):** the device reads its own
  `canonical_parent` via `live.object` to get its track's LOM id, then reads
  `live_set`'s ordered `tracks` / `return_tracks` / `master_track` id lists and
  finds its position - that position is the track `index`, and which list it was
  found in is the `kind`. This is done entirely with `live.object` queries driven
  by a `metro` (which also beats the Node-for-Max boot race - a one-shot load
  message is lost while Node is still starting).
- **Transport:** `registry-client.js` (Node for Max) is a TCP *client* that
  connects out to `127.0.0.1:9878`, sends a `hello` frame with the resolved
  identity (`uuid`/`index`/`kind`), then streams per-100ms `block` frames.
  Reconnects automatically if the MCP server restarts.
- **Registry:** the MCP server (`ableton_mcp_max/tap_registry.py`) hosts the
  listening socket on a background thread, keyed by a stable per-device `uuid`,
  and evicts a tap's state when its connection drops.
- **DSP (Phase 1 = levels):** `plugin~` -> two-stage `biquad~` BS.1770
  K-weighting -> square -> 100 ms mean-square (loudness), plus `peakamp~` ->
  sample-peak. All gating/integration math lives in
  `ableton_mcp_max/loudness_utils.py`; the device is a dumb relay. **8-band
  spectrum and stereo (mid/side) are added in later phases** (the `block` frame
  already carries zeroed `bands`/`mid`/`side` slots for forward compatibility).

## Building / editing the device
The shipped `MCP Tap.amxd` is generated by grafting the measurement + identity
chain onto a known-good M4L wrapper (the `.amxd` is `ampf`/`meta`/`ptch` chunks
around the patcher JSON; keep the template `plugin~`/`plugout~` + wrapper, swap
`boxes`/`lines`). `MCP Tap.maxpat` is the editable patcher source;
`registry-client.js` is the relay source of truth.

Live gotchas: `live.path this_device` only ever emits the device's `id` (no path
output) - resolve the track via `live.object` `get canonical_parent` +
`live_set` track-list position instead; M4L `loadbang` is unreliable, use
`live.thisdevice`; Node boots in ~1-2 s so identity must be re-sent (a `metro`),
not a one-shot.

## Accuracy notes
- K-weighting + true-peak chain is inherited from the Ozone-validated v0.7.0 tap
  (loudness within <1 LU, peak within ~0.1-0.3 dB).
- True-peak is currently sample-peak (no 4x oversampling).
- K-weighting coefficients are the 48 kHz set; the device reports its actual
  sample rate and `loudness_utils` derives block duration from it.
